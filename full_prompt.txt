🚨 CRITICAL BUGS FOUND:
Bug #1 — Hash Collision in Order Book (P&L Impact: HIGH)
cpp
size_t idx = order.price & (MAX_LEVELS - 1);  // 131072 levels
if (bids_levels_[idx].price != 0 && bids_levels_[idx].price != order.price) 
    return false; // Hash collision — order REJECTED
Problem: The order book uses a power-of-2 hash table with open addressing. If two prices hash to the same bucket, the second price is rejected entirely.
Institutional impact: In a real market with 131,072 possible hash slots and instruments spanning wide price ranges, collisions are guaranteed under the birthday paradox. Orders will be silently rejected.
Fix: Use chaining (linked list per bucket) or a proper flat hash map (e.g., ska::flat_hash_map, absl::flat_hash_map). For HFT, use a dense price array if tick size is fixed.
Bug #2 — Memory Leak in Destructor
cpp
~OrderBook() {
    for(size_t i=0; i<MAX_LEVELS; ++i) {
        delete bids_levels_[i].q;
        delete asks_levels_[i].q;
    }
}
Problem: bids_levels_ and asks_levels_ are stack arrays of 131,072 Level structs each. The destructor iterates all 262,144 slots on every destruction. For a system with 10,000 instruments, that's 2.6 billion delete calls on shutdown.
Fix: Use a pooled allocator or std::unique_ptr with lazy initialization. Only delete non-null queues.
Bug #3 — add_bid_level / add_ask_level Memory Safety
cpp
if (!bids_levels_[idx].q) bids_levels_[idx].q = new OrderQueue<256>();
*bids_levels_[idx].q = q;  // COPY assignment of 256-entry queue
Problem: These are public methods used by load_snapshot. They do a full bitwise copy of OrderQueue<256> (including raw array). If q is a local stack variable, this is fine, but if q contains pointers, it's a shallow copy disaster. Currently safe because OrderQueue is POD, but fragile.
Bug #4 — Missing Cancel-Replace Support
The engine supports cancel_order but not modify/replace. In institutional trading, ~40% of order flow is cancels/replaces. Missing this means the engine cannot handle real market dynamics.
Bug #5 — Snapshot Format is Not Version-Safe
cpp
std::fwrite(&id, sizeof(id), 1, f);
std::fwrite(&bids, sizeof(bids), 1, f);
No CRC, no endianness marker, no schema version. Cross-platform recovery is impossible.
Performance Note:
insert_active_bid uses std::memmove on every insertion. For 256 levels, worst case is O(256) with 256×8=2048 bytes moved. At 1M orders/sec, this is ~2GB/s of memory bandwidth just for level maintenance. Consider a heap-ordered array or skip list for O(log n) insertion.

Issue #1 — LAST_TRADE_PRICES is a static array with interior mutability
rust
static LAST_TRADE_PRICES: [AtomicU64; 4096] = { const INIT: AtomicU64 = AtomicU64::new(0); [INIT; 4096] };
Clippy warning suppressed: #[allow(clippy::declare_interior_mutable_const)]
Problem: This is actually safe in Rust because AtomicU64 is Sync, but it's a code smell. A once_cell::Lazy<Box<[AtomicU64]>> would be cleaner.
Issue #2 — Duplicate detection is O(4096) linear scan
rust
fn check_duplicate(&self, order: &Order) -> bool {
    for &(id, ts) in self.recent_orders.iter() { ... }
}
For a system targeting <500ns p99, a 4096-iteration loop on every order is ~2–5 µs depending on cache state. This violates the stated latency target.
Fix: Use a Robin Hood hash set or a bitmask Bloom filter for O(1) duplicate detection.
Issue #3 — Velocity check has off-by-one in window logic
rust
let lookback_idx = (self.velocity_head + VELOCITY_RING_SIZE - self.max_velocity) % VELOCITY_RING_SIZE;
let oldest_ts = self.velocity_ring[lookback_idx];
oldest_ts > 0 && now_ns.saturating_sub(oldest_ts) < self.velocity_window_ns
Problem: This checks if the Nth-ago order is within the window, but does not count how many orders are actually in the window. If max_velocity=100 and 99 orders arrived 500ms ago and 1 order arrived now, it passes. If 100 orders arrived 999ms ago and 1 order arrived now, it fails even though only 1 order is in the current 1s window.
Fix: Maintain a sliding window queue and count entries within [now - window, now].
Issue #4 — Greeks calculation uses libm::erf
rust
let nd1 = 0.5 * (1.0 + libm::erf(d1 / 2.0_f64.sqrt()));
Problem: libm::erf is a software implementation. For production options risk, you need Intel SVML or hardware-accelerated erf (AVX-512). At 100K options quotes/sec, this is a bottleneck.
Also: Black-Scholes assumes constant volatility and no dividends — not suitable for American options or dividend-paying stocks.
Issue #5 — calculate_var is parametric, not Monte Carlo
rust
pub fn calculate_var(&self, portfolio_value: f64, volatility: f64, ...) -> VaRResult {
    let z_95 = 1.645f64;
    ...
    method: "parametric",
}
The comment says "Monte Carlo VaR simulation" but the implementation is parametric (variance-covariance). For a portfolio with non-linear derivatives, parametric VaR is inaccurate.
Fix: Implement actual Monte Carlo with Cholesky decomposition of the correlation matrix, or use historical simulation with weighted returns.
Issue #6 — update_pnl updates position on fill, but check_order does NOT commit position
rust
// In check_order:
// "All checks passed — DO NOT commit position optimistically here.
// Positions should only be updated in update_pnl upon receiving actual fills."
Good: This is correct. Pre-trade position checks are soft blocks (optimistic), and true position updates happen post-fill.
But: There is a race condition window between check_order returning Approved and update_pnl being called. If two orders for the same instrument are in flight, both could pass position checks based on stale position data, then both fill, exceeding the limit.
Fix: Use an optimistic position reservation (decrement available capacity in check_order, release on reject, confirm on fill).

Bug #2 — SendOrderToAlpaca Does Not Validate Response

Problem: Alpaca Paper API returns 200 for immediate fills and 202 for accepted orders. But the code does not check if the order was actually accepted — it only checks HTTP status. A 202 with an error body would be treated as success.
Fix: Parse Alpaca's JSON response and check for status field values (accepted, pending, rejected).

Bug #4 — Race Condition in MatchingEngineClient.ioLoop
go
func (c *MatchingEngineClient) ioLoop() {
    for cmd := range c.cmdCh {
        c.mu.Lock()
        if c.conn == nil { ... }
        conn := c.conn
        reader := c.reader
        c.mu.Unlock()
        // ... use conn and reader without holding lock
    }
}
Problem: conn and reader are captured under the lock, then used without the lock. Another goroutine could call Connect() and replace c.conn between c.mu.Unlock() and fmt.Fprint(conn, ...). The old conn is still valid (not closed), but if the new connection is established, health checks might report the new connection while I/O happens on the old one.
Fix: Hold the lock for the entire I/O operation, or use a sync.RWMutex with read lock during I/O.
Bug #5 — HotReloadConfig Does Not Roll Back on Persist Failure
go
o.configMutex.Lock()
old := o.config
o.config = newConfig
o.configMutex.Unlock()

if err := o.persistConfig(); err != nil {
    o.logger.Error("failed to persist config", "error", err)
    // NO ROLLBACK — newConfig is already active!
}
Problem: If disk write fails, the in-memory config is updated but the disk state is stale. On next restart, the old config loads, creating a split-brain between running instance and persisted state.
Fix: Persist first, then swap in-memory config atomically.
Bug #6 — symbolMap is Hardcoded
go
symbolMap := map[string]uint64{
    "BTC/USD": 1, "ETH/USD": 2, "AAPL": 3, ...
}
Problem: Symbols are compiled into the binary. Adding a new symbol requires recompilation and redeployment. In production, symbol mappings must be loaded from a database or config service at runtime.
Fix: Load from SQLite on startup, with a cache refresh interval.
Bug #7 — /order Handler Returns 200 OK Before Order is Processed
go
w.WriteHeader(http.StatusOK)
// ... then fires goroutine to actually send to matching engine
Problem: The HTTP response returns 200 OK with status "WORKING" before the order ever reaches the matching engine. If the matching engine is down, the client thinks the order is working but it was never submitted. This violates idempotency and best execution obligations.
Fix: Synchronously validate and enqueue, then return. Or return 202 Accepted with a location to poll.
Bug #8 — cancel_order in C++ engine is not called from Go gateway
The Go gateway has a DELETE /order/{cl_ord_id} endpoint, but it only updates the in-memory state machine and SQLite. It never sends a cancel to the C++ matching engine. The order remains active in the engine's order book.
Fix: Forward cancel requests via the MatchingEngineClient TCP connection.
Bug #9 — OrderRequest.UnmarshalJSON Has Dangerous Float Parsing
go
case float64:
    if math.Abs(val) < 1e7 && val != 0 {
        return int64(math.Round(val * 1e8))
    }
    return int64(math.Round(val))
Problem: The condition math.Abs(val) < 1e7 is arbitrary. A price of 10,000,000.01 would be returned as 1000000001 (not multiplied by 1e8), while 9,999,999.99 would be 99999999900000000. This is a silent data corruption bug for large prices.
Fix: Always expect fixed-point integers in JSON, or use a strict decimal parser.

Issue #1 — Spoofing Detection is Trivial

The actual SpoofingDetector implementation is in lib.rs (not fully shown), but based on the README, it's "pattern-based: large order + rapid cancel within configurable window."

Issue #2 — No Live SHM Subscription
The README states: "No live SHM subscription yet (demo mode)". The daemon generates synthetic orders when SHM is unavailable.
Problem: In production, this means the compliance engine is not actually watching real trades. It's a compliance theater.
Issue #3 — Audit Log is Not Tamper-Evident
rust
// WORM log with SHA-256 chain
The README claims "chain-verifiable", but the code shows no Merkle tree, no HSM-signed timestamps, no append-only filesystem (e.g., chattr +a), and no remote replication. A root user can still rm -f logs/audit.log.
Fix: Use append-only ext4 attributes, write to WORM storage (e.g., AWS Glacier), and sign each record with an HSM.
