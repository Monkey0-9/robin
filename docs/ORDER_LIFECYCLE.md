## 2. Order Identity Model

Every order maintains strict canonical identifiers across its entire lifecycle:

| Field | Type | Description |
| :--- | :--- | :--- |
| `client_order_id` | `string` / `uint64` | Client-assigned idempotent correlation token |
| `order_id` | `uint64` | Internal monotonic sequence generated via steady-clock anchor |
| `execution_id` | `uint64` | Unique fill identifier generated by matching engine / venue |
| `venue_order_id` | `string` | Downstream exchange-assigned order identifier |
| `parent_order_id`| `string` | For TWAP/VWAP/Bracket child slice linkage |
| `replace_id` | `string` | For atomic Cancel-Replace (OUCH Cancel-Replace / FIX 35=G) |

## 3. Invariants & Guarantees

1. **Cancel Integrity:** A client cancel request (`DELETE /order/{cl_ord_id}`) enters `CANCEL_PENDING`, transmits a cancel packet into the C++ matching engine's SPSC ring, and only transitions to `CANCELED` upon engine acknowledgment.
2. **Double-Spend Prevention:** Pre-trade risk checks create an optimistic position/credit reservation. If rejected or cancelled, the reservation is rolled back atomically.
3. **Deterministic Serialization:** Order transitions are recorded to write-ahead logs (`async_db.go` WAL) prior to external confirmation.
